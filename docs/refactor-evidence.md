# 挙動を変えない整理の記録

おつかいめいろのコードを整理したとき、「挙動と見た目を変えていない」ことをどう確かめたかの記録です。数字はすべて作業中の実測の記録から写しています。対象は作業前の `820955f` から `0c836fc` までのコミットです。

## 何をしたか

整理は次の 6 段階で、段階ごとにコミットしました（71 ファイル、+3543 / −789 行）。約束は「挙動と見た目は変えない」の 1 つです。例外は段階 6 の不具合 3 件の直しだけで、これは直す前と直した後を実際の操作で測りました。

| 段階                       | 中身                                                                                                                                      | コミット                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 1 レイアウトの式           | 配分計算・寸法の見積もり・探索・色決めを純関数に切り出し、テストを足す                                                                    | 5ebb47b・61a2b84・c4a5aa0 |
| 2 同じ値を 1 か所に        | 枠の幅と余白・方向パッドの寸法・影・アバターと障害物の絵・⭐の数                                                                          | 4242d87                   |
| 3 保存の読み書きと音まわり | 先に今の取り出し方をテストで固定してから、web のグローバルと localStorage の入口を 1 つにまとめる（15 か所の取り出しと 3 つの保存の入口） | 06045ed・fbf3185          |
| 4 小さなまとめ             | 「1 回だけ呼ぶ」包み・方向の表・おとなモードの確認ボックス                                                                                | d11de27                   |
| 5 使われていない定義       | 使われていない定義と引数を消し、テンプレート JSON の検査を足す                                                                            | 8998608                   |
| 6 不具合 3 件              | 下の「不具合 3 件」                                                                                                                       | 5d7bcdf・24a7e0a          |

## 撮影の比べ方

各段階の前後の版を同じ手順で撮り、すべてを突き合わせました。

- 画面幅 4 つ: 320×568 / 390×844 / 844×390 / 1280×800。状態は見た目 31（タイトル、レベルえらび、プレイ①②、ついたね!、がんばりカード、おとなモードの各表示）と音 7。組み合わせて 233 組です（音の状態は 390×844 だけ）。
- 比べるもの: 全画素（許容 0）、DOM と計算後のスタイルの全数、localStorage の中身、コンソールの警告、音の記録（効果音・声・BGM）。1 つでも違えば「差分あり」です。
- 操作は実際のマウスの押下です。押す先が目的の要素であることを確かめてから押します。
- 決定性の工夫: 乱数を種つきのものに差し替え、迷路を作る直前に種を入れ直す。時計は止め、進めるのは明示した分だけ。React のスケジューラと ResizeObserver も止めた時計に載せる。撮る直前に描画を取り直し、連続 2 枚が一致するまで撮る。

## 揺れの扱い

工夫をしても、同じ版を 2 回撮ると差が出る組がありました。隠さずに書きます。

- 同じ版を 2 回撮った結果: 233 組のうち差分 0 が 229、差分ありが 3、片方欠けが 1。欠けの 1 は撮影手順の誤り（ボタンの探し方）で、直して撮り直すと一致しました。差分ありの 3 は画素だけの差（1・964・1537 画素）で、DOM・計算後のスタイル・保存値・警告は一致していました。どれも、ゴールの拍動など変換が掛かった要素の縁の描画が外れる揺れです。
- 作業前の版を撮ったときにも 1 組（3 画素）出ました。この撮影は、撮り直すと 2 通りの画像が出ます。

そこで判定の規則を決めました。画素だけ違う組は、新しい版を 5 回撮り直し（決まらなければ 9 回）、過半数が前の版と一致すれば 1 回目を外れ値とみなします。DOM・保存値・警告の差と、撮り直しても一致しない差は揺れとして扱いません。外れ値の元の画像は消さずに残しました。

規則どおりに決まらなかった、または規則を広げたものが 2 つあります。

- 段階 4 のクリア演出の途中の 1 組（3 画素）は、9 回撮り直して前の版と一致したのが 3 回でした。画像は 2 通りだけで、前の版の画像が 3 回以上出たので、2 通りに揺れる撮影として外れ値にしました。
- 段階 5 では音の記録の差が 1 組ありました。ファンファーレの 3 音の開始が 0.05 秒の目盛りで 1 つずつずれただけで、設計値（0.125・0.375・0.625 秒）がちょうど目盛りの境目にあります。この段階は音のタイミングを変えていないので、規則を音の記録にも広げ、5 回撮り直して 5 回とも前の版と一致しました。

## 変異テスト

足したテストが本当に効いているかを、ソースに変異を 1 つずつ当てて確かめました。壊す変異はテストが落ちること、同じ意味の書き換えはテストが通ったままであることを期待します。1 件ごとにファイルを元のバイト列へ戻し、ハッシュの一致を確かめました。

| 段階                       | 件数 | 期待と違った結果 |
| -------------------------- | ---- | ---------------- |
| 1 レイアウトの式           | 51   | 0                |
| 1 の仕上げ                 | 17   | 0                |
| 2 同じ値を 1 か所に        | 24   | 0                |
| 3 の前に足したテスト       | 19   | 0                |
| 3 保存の読み書きと音まわり | 39   | 0                |
| 4 小さなまとめ             | 15   | 0                |
| 5 使われていない定義       | 27   | 0                |
| 合計                       | 192  | 0                |

例（式の係数を変えると落ちるテスト）:

- `src/layout.ts` の盤の枠線の太さ 3 → 2: 18 本中 5 本が落ちる。落ちたテストの 1 つは「盤の枠線の太さ 3（MazeGrid の描画と、PlayScreen のマスの計算が同じ値を使う）」。
- `src/game/dirPad.ts` の高さの係数 3.3 → 3.2: 17 本中 10 本が落ちる。1 つは「高さの見積もり（切り上げた 一辺 × 3.3）は、実際のパッドの高さ（ボタン 3 つ + 行間 2 つ）以上」。
- `src/game/dirPad.ts` の幅の係数 3.4 → 3.0: 17 本中 3 本が落ちる。1 つは「幅の見積もり（一辺 × 3.4）は、実際のパッドの幅（ボタン 3 つ + 列間 2 つ）以上（一辺 50 以上）」。

同じ意味の書き換えの例: `frameInnerWidth` を「余白 × 2 を 2 回引く」書き方にすると、20 本すべて通ったままでした。

## 不具合 3 件

整理の途中で見つけた 3 件だけは挙動を変えました。直す前に実際の操作で再現し、直した後に同じ操作で再現しないことを確かめています。

| 件                                                                         | 直す前                                                                                       | 直した後                                                                                                                             |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| M-B1（High）録音の準備中におとなモードを離れると、離れたあとに録音が始まる | 再現した。保存された声が `[]` → 6 秒後に `["tsuita"]`。離れた直後のマイクのトラックは `live` | 再現しない。トラックはすぐ `ended`、6 秒後も保存なし                                                                                 |
| M-B2（Low）タイトルの長押しのタイマーが画面を離れても残る                  | 再現しなかった。Web 版では、画面が外れるときに押下の終了処理がタイマーを消す                 | ネイティブで終了処理が呼ばれない場合に備えた防御的な直し。同じ操作で再現しない（足した後始末がタイマーを消すことを呼び出し元で確認） |
| M-B3（Low）② の実行中に画面の大きさが変わると、アバターが 1 マス前へ跳ぶ   | 再現した。マス 80 → 51 の切り替えで、40ms に (−87, −38.1)px 動き、スタートのマスに重なる     | 再現しない。(0, −11.1)px と滑らかに動く。対照の操作（直した箇所を通らない経路）の (0, −14.3)px と同じ種類の動き                      |

M-B3 は、最初の判定の条件（進み量が 0.2 マス以上減る）では直した後も「再現」と出ました。直した後の動きは対照と同じだったので、印を「スタートのマスへ合わせ直された」に直して測り直しています。
